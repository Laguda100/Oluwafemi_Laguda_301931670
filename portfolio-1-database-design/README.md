## 1. Relational schema

Notation: PK is underlined (shown here in bold), FK is marked with an arrow to its parent.

- **faculty**(**faculty_id**, code UK, name UK)
- **department**(**department_id**, faculty_id → faculty, code UK, name), UK(faculty_id, name)
- **programme**(**programme_id**, department_id → department, code UK, name, degree_type, duration_years)
- **lecturer**(**lecturer_id**, department_id → department, staff_no UK, title, first_name, last_name, email UK, academic_rank)
- **student**(**student_id**, matric_no UK, programme_id → programme, first_name, last_name, other_names, email UK, date_of_birth, gender, entry_year, current_level, status, created_at)
- **course**(**course_id**, department_id → department, course_code UK, title, credit_units, course_level, semester)
- **academic_session**(**session_id**, name UK, start_date, end_date, is_current)
- **course_offering**(**offering_id**, course_id → course, session_id → academic_session, lecturer_id → lecturer, capacity, result_status), UK(course_id, session_id)
- **registration**(**registration_id**, student_id → student, offering_id → course_offering, registered_at, status), UK(student_id, offering_id)
- **result**(**registration_id** → registration, ca_score, exam_score, total_score *(generated)*, entered_by → lecturer, entered_at, updated_at)
- **grade_scale**(**grade**, min_score UK, grade_point UK)
- **result_audit**(**audit_id**, registration_id, action, old/new ca & exam scores, changed_by, changed_at)

## 2. Keys

| Decision | Reason |
|---|---|
| **Surrogate PKs** (`GENERATED BY DEFAULT AS IDENTITY`) | Natural identifiers such as matric numbers, course codes and staff numbers can change (re-coding, a typing error at admission). A surrogate key means every FK pointing at the row stays valid. Integer keys also make joins and indexes smaller and faster than `VARCHAR` keys. |
| **Natural keys kept as `UNIQUE`** | `matric_no`, `course_code`, `staff_no` and `email` remain unique, so the surrogate key never allows duplicate real-world entities. |
| **Composite candidate keys** | `UNIQUE(course_id, session_id)` means a course runs only once per session. `UNIQUE(student_id, offering_id)` means a student can't register twice for the same course. |
| **`result.registration_id` is both PK and FK** | Makes the relationship exactly 1 : 0..1. A result can't exist without a registration, and a registration can't have two results. |
| **Smallest type that fits** | `SMALLINT` for small lookup tables, `BIGINT` for `registration`, the fastest-growing table (students × courses × sessions). |

## 3. Constraints and business rules

| Rule | How it is enforced |
|---|---|
| CA is out of 30, exam out of 70 | `CHECK (ca_score BETWEEN 0 AND 30)`, `CHECK (exam_score BETWEEN 0 AND 70)` |
| Total always equals CA + exam | `GENERATED ALWAYS AS (ca_score + exam_score) STORED`, which cannot be written directly |
| Identifier formats | Regex `CHECK`s on `matric_no` (`CFU/2025/00001`), `staff_no`, `course_code`, email, session name |
| Only one current session | **Partial unique index** `ON academic_session(is_current) WHERE is_current` |
| Session ends after it starts | Table-level `CHECK (end_date > start_date)` |
| Valid enumerations | `CHECK ... IN (...)` for gender, status, rank, degree type, level, semester |
| Results can't change after Senate approval | `BEFORE` trigger `trg_result_guard` raises an error when the offering is `APPROVED` |
| Every score change is traceable | `AFTER` trigger `trg_result_audit` writes old and new values, the user and the time to `result_audit` |
| No orphan or accidental deletes | All FKs use the default `NO ACTION`/`RESTRICT`. Academic records must never be cascade-deleted. |

**Why `CHECK ... IN` instead of PostgreSQL `ENUM` types?** Adding a value to a CHECK list is a simple `ALTER TABLE`. An ENUM value can't easily be removed or reordered.

## 4. Normalisation

### Starting point: the paper result sheet (UNF)

Departments traditionally keep results as a spreadsheet like this:

| matric_no | student_name | programme | department | faculty | session | course_code | title | units | lecturer | ca | exam | total | grade | gp |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| CFU/2025/00001 | Oluwaseun Adeleke | B.Sc. CS | Computer Science | Computing & Applied Sci | 2025/2026 | CSC 101, MTH 101, ... | ... | 3, 3, ... | ... | ... | ... | ... | ... | ... |

Problems with this layout:
- **Repeating groups.** One student row holds many courses.
- **Update anomaly.** Renaming a course title means editing every row of every student who took it.
- **Insert anomaly.** A new course can't be recorded until a student registers for it.
- **Delete anomaly.** Deleting the last student who took a course also deletes the course's details.

### 1NF: atomic values, no repeating groups

Each row is split into one row per student, per course, per session. Candidate key: **(matric_no, course_code, session)**.

### 2NF: remove partial dependencies on part of the composite key

| Functional dependency | Depends on only part of the key | New relation |
|---|---|---|
| matric_no → student_name, programme, … | matric_no | **student** |
| course_code → title, units, department, semester | course_code | **course** |
| session → start_date, end_date | session | **academic_session** |
| (course_code, session) → lecturer | course + session, not the student | **course_offering** |

What remains depends on the whole key: (student, offering) → ca, exam. That becomes **registration** + **result**.

### 3NF: remove transitive dependencies

| Transitive dependency | Fix |
|---|---|
| student → programme → department → faculty | Store only `programme_id` on student. Programme, department and faculty become their own tables. |
| course → department → faculty | Course stores `department_id` only. |
| result → total → grade → grade_point | **grade** and **grade_point** are not stored at all. They are looked up from **grade_scale** in `v_student_result`, so if Senate changes the grading policy only one table changes. |
| GPA / CGPA | Never stored. Computed by `v_semester_gpa` and `v_cgpa`, so they can never be out of date. |

### BCNF check

In every table, every determinant is a candidate key:
- `student`: `student_id`, `matric_no` and `email` each determine all other attributes, and all three are keys (PK or UNIQUE).
- `course_offering`: determinants are `offering_id` and `(course_id, session_id)`. Both are keys.
- `registration`: determinants are `registration_id` and `(student_id, offering_id)`. Both are keys.
- `grade_scale`: `grade`, `min_score` and `grade_point` are each UNIQUE, so each is a candidate key.

The schema is therefore in **BCNF**.

### One deliberate exception: `total_score`

Strictly, `total_score` depends on `(ca_score, exam_score)`, which is a transitive dependency. I kept it as a **stored generated column** because:
1. The DBMS computes it, so it can't become inconsistent. The update anomaly that normalisation prevents can't happen.
2. It can be indexed. Portfolio 2 uses it to find all failed results (`total_score < 40`) without scanning the whole table.

## 5. How to run

From the repository root in PowerShell:

```powershell
docker compose up -d                        # start PostgreSQL 16 (wait about 10 s for "healthy")
docker compose ps                           # STATUS should say (healthy)
.\portfolio-1-database-design\run.ps1        # runs scripts 01 to 05 in order
```

To open an interactive SQL shell:

```powershell
docker exec -it crestfield-pg psql -U portal_admin -d result_portal
```

Useful psql commands: `\dt` (tables), `\d+ result` (one table's structure), `\di` (indexes), `\dv` (views).

## 6. How it was tested

1. **Schema builds cleanly.** `01_schema.sql` runs with `ON_ERROR_STOP=1`, so any error stops the run.
2. **Constraint tests.** `04_constraint_tests.sql` tries 9 invalid operations and 1 valid one. Every line of output should start with `PASS`:

   | Test | Attempt | Expected rejection |
   |---|---|---|
   | T1 | exam score 85 | `check_violation` (23514) |
   | T2 | duplicate registration | `unique_violation` (23505) |
   | T3 | bad matric format | `check_violation` (23514) |
   | T4 | registration for missing student | `foreign_key_violation` (23503) |
   | T5 | second current session | `unique_violation` (23505) |
   | T6 | edit an approved result | trigger exception (P0001) |
   | T7 | delete a department that has programmes | `foreign_key_violation` (23503) |
   | T8 | write `total_score` directly | `generated_always` (428C9) |
   | T9 | lecturer with no department | `not_null_violation` (23502) |
   | T10 | a valid result | accepted, then rolled back |

3. **Business output.** `05_verify.sql` shows the transcript, GPA, CGPA ranking and audit trail. These can be checked by hand. For example, 3 units × grade point 5 = 15 quality points.
